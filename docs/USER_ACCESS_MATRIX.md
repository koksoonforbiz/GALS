# User Access Matrix

Satisfies SMU Cybersecurity Checklist item 2 ("detailed user access matrix for
the service(s)/system(s)"). Generated by reading every `*.controller.ts` file
in `apps/api/src` directly — this is what the code actually enforces, not a
design intention. Regenerate whenever routes/roles change materially.

## Roles

Three roles exist system-wide: **student**, **teacher**, **admin**
(`packages/shared/src/roles.ts`). There is no separate "researcher" or
"super-admin" role in the application layer — an `admin` account is the
highest privilege level the app itself grants.

## How access control is enforced

Every route is guarded by `JwtAuthGuard` (valid session required) and, where a
role restriction applies, `RolesGuard` reads a `@Roles(...)` decorator and
allows the request only if the caller's role is in that list (OR logic — a
route requiring `['teacher','admin']` accepts either). A route with no
`@Roles()` at all is reachable by **any authenticated user regardless of
role** — access is then enforced by the service layer instead (e.g. a student
can only fetch their own chat history, not another student's, checked in code
against `req.user.id`, not by the route guard).

## Public routes (no authentication required) — the complete list

Every unauthenticated route in the system, with no exceptions:

| Route                   | Why                                                                                                                                                                                                                                                                                                                                               |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /health`           | Liveness/readiness probe — standard to leave open; reveals DB/blob/event-bus health status only.                                                                                                                                                                                                                                                  |
| `POST /auth/register`   | Account creation — necessarily pre-authentication.                                                                                                                                                                                                                                                                                                |
| `POST /auth/login`      | Necessarily pre-authentication.                                                                                                                                                                                                                                                                                                                   |
| `POST /auth/2fa/verify` | Part of the login challenge flow, before a session exists.                                                                                                                                                                                                                                                                                        |
| `POST /auth/2fa/resend` | Same.                                                                                                                                                                                                                                                                                                                                             |
| `POST /dev/seed`        | **Not guarded by NestJS at all** — access is enforced only inside the handler body via `NODE_ENV === 'development'` (fails closed if unset, fixed earlier in this project). Flagged here because it's a business-logic gate, not an access-control-layer gate — worth knowing precisely how this one differs from every other route in the table. |

## Any-authenticated-user routes (66) — where and why

Concentrated in a few controllers that intentionally enforce authorization in
the _service_ layer (per-resource ownership) rather than the _route guard_
layer, because the restriction is "your own data," not "your role":

| Controller                                                                      | Routes | Pattern                                                                                                                                                                                                                                     |
| ------------------------------------------------------------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `learning-interventions.controller.ts`                                          | 26     | Practice testing, interrogative elaboration, stepwise learning, distributed practice, saved reviews, chat — all scoped to `req.user.id` in the service layer. Only its `prompt-config` sub-group (teacher-authored settings) is role-gated. |
| `code-decomposition.controller.ts`                                              | 15     | Entire controller — session ownership checked in code, not by role.                                                                                                                                                                         |
| `auth.controller.ts`                                                            | 7      | Self-service account actions (logout, 2FA enrollment/disable, TOTP setup, `/auth/me`) — inherently "about the caller," not role-scoped.                                                                                                     |
| `blob.controller.ts`                                                            | 5      | Object-storage presign/upload/download/delete — ownership checked via `assertOwnsAttemptKey`.                                                                                                                                               |
| `courses.controller.ts`                                                         | 3      | Course listing/catalog/detail — readable by any enrolled or browsing user.                                                                                                                                                                  |
| `assessments.controller.ts`, `topics.controller.ts`                             | 2 each | List/detail reads.                                                                                                                                                                                                                          |
| `chat-history.controller.ts`                                                    | 2      | Scoped to `req.user.id`.                                                                                                                                                                                                                    |
| `webgazer`, `pupil-size`, `attempts`, `modules/items` (`ItemActionsController`) | 1 each | Single export/download routes.                                                                                                                                                                                                              |

## Known gaps this matrix surfaces (for the compliance response, not hidden)

- `POST /dev/seed` has no route-level guard — flagged, not fixed, since its
  in-handler `NODE_ENV` check is a deliberate design already reviewed this
  project; worth a second look before production regardless.
- 66 routes rely on service-layer (per-resource) authorization rather than
  route-level role checks. This is a legitimate, common pattern (a student
  shouldn't be _role_-restricted from their own chat history, they should be
  _ownership_-restricted from someone else's) but it means this matrix alone
  doesn't fully describe authorization for those 66 routes — the enforcement
  lives in each service's query filters (e.g. `where: { studentId: req.user.id }`),
  not in a decorator. Worth a dedicated code-level review pass confirming
  every one of those filters is actually present and correct, since a missed
  filter there wouldn't show up in a route-decorator audit like this one.
