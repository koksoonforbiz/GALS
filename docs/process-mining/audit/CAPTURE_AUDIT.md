# GALS capture audit for process mining (Prompt A)

**Scope.** Read-only audit of how the GALS platform captures learner actions, turns them into learning events, exports them, and how GALS Studio ingests and replays them, measured against requirements R*, A* and V\* in `docs/process-mining/gals-pm-prompts/02_RESEARCH_REQUIREMENTS_process_mining.md`.
**Code audited.** Branch `course-prompting-kt`, HEAD `acee9b6` (2026-11-25), the commit running on gals.foodai.org.
**Method.** Static reading of the code with `path:line` evidence; read-only counts from the laptop's local dev database (fixtures and e2e runs only, no real learners); three findings re-checked against real bundles exported from the server on 2026-11-24 (see "Verification notes"). No source, schema, config or database was changed.
**Companion files.** `action_catalogue.csv` (175 action types, one row each), `STUDIO_ARCHITECTURE.md` (A8).

**The five findings that matter most:**

1. **Learning events cannot be traced back today.** Their ids are regenerated on every recompute and earlier versions are deleted (CAP-60, CAP-61), and the export bundle drops their source action ids, measured values and platform id, while activity rows go out with no id at all (CAP-69/80, CAP-81). GALS Studio stores learning events but shows them nowhere (STU-01 to STU-03). Prompt D's verdicts have nothing stable to attach to until Prompt B fixes this.
2. **Learner free text is logged without text-capture consent** outside the lessons: Learning Assistant messages and replies (up to 1,000 characters each), Mode B messages, practice and stepwise answers, and 50 characters of the text of every clicked element (CAP-30, same as CAP-05; verified in the code). This affects data being collected on the live site now.
3. **Events can be lost without a record.** A database error on the batch endpoint still returns OK and the browser throws the batch away (CAP-40, verified); one invalid event rejects its whole batch of up to 500 (CAP-41); there is no event id, sequence number, server-received time, persistent buffer or gap detection (CAP-43 to CAP-45); replay snapshots sent on tab hide exceed the keepalive limit (CAP-46, needs a runtime check).
4. **Mode B is almost unlogged** (CAP-20, Blocker if Mode B is used in the study), and **intervention uptake (M34) is wrong**: `INTERVENTION_TRIGGERED` mixes learner-launched strategies with system nudges, so locally all 30 M34 detections come from learner-initiated rows (CAP-01).
5. **No unclassified-time measure and no `NO_PATTERN`/`UNRESOLVED`** (CAP-65, CAP-66): coverage (A5) cannot be reported, and incomplete cases are forced into a label or dropped.

**Good news against file 01.** Tab-close sessions are now closed and parsed: a server-side sweeper closes sessions after 2 hours without activity and fires `session.closed` (`session-timeout.sweeper.ts`, commit `7ae4a96`). Learning events are already in the bundle (`derived/learning_events.jsonl`), just without provenance.

## A1. Learning-action emitters

### Summary

- **106** values in the Prisma `ActivityAction` enum (`apps/api/prisma/schema.prisma:176-331`). The API TypeScript enum (`apps/api/src/activity-log/activity-action.enum.ts:1-149`) matches it exactly. The web union type (`apps/web/src/lib/activity-log/types.ts:1-104`) has 91 values: it leaves out the 15 server-only values (EF*\*, GATE_UNLOCKED, KNOWLEDGE_TEST_SUBMITTED/GATE_BLOCKED, PRACTICE_TEST_CONFIGURED, CODE_DECOMP*\*). That is correct for blinding (`activity-action.enum.ts:151-175`, rejected at `apps/api/src/activity-log/dto/log-event.dto.ts:10-12`).
- **97 action types are written to `activity_logs` by code. 9 enum values have no emitter.** 66 types are written only by the browser, 24 only by the server, and 7 by both. All 7 are double emitters (finding 3).
- Writers: one browser spine and 13 server modules.
  - **Browser:** every call goes through `track()` (`apps/web/src/lib/activity-log/ActivityLogContext.tsx:142-152`). Events are buffered and POSTed to `/api/activity-log/batch` every 30 s, on `visibilitychange: hidden` and `pagehide` (keepalive, 60 KB chunks), and on logout. Calls come from 18 files (plus `slides.tsx` and `PromptLab.tsx`, which reach `track()` through `emit`): the lesson tracker, the Prompt Lab, the chatbot, 4 strategy views, the dialogue page, the review queue, assessments, knowledge tests, notes, biometrics, the camera guard, the layout and the route tracker.
  - **Server:** `ActivityLogService.record()` (`apps/api/src/activity-log/activity-log.service.ts:38-61`) is called by 12 server modules: session, attempts, dialogue, learning-interventions, code-decomposition, efa, knowledge-tests, course-gates, recording, pupil-size, webgazer and pyfeat. The 13th, the nudge engine, writes its row directly with `prisma.activityLog.create` (`apps/api/src/learning-events/nudges/nudge.service.ts:293`).
- The full per-action inventory is `docs/process-mining/audit/action_catalogue.csv` (175 rows: 106 enum values, 52 library-only names, 17 non-`activity_logs` stores).

### Method

1. Took the enum values from `schema.prisma`, the API enum and the web union, and diffed them.
2. For each value, grepped `apps/web/src` for `'VALUE'` (leaving out `types.ts`, the teacher replay/export lists and tests) and `apps/api/src` for `ActivityAction.VALUE` / `action: 'VALUE'` (leaving out specs and the enum file). Then read every hit to confirm it really writes a row, and to get its trigger and payload.
3. Interactive-lesson events are named indirectly. Course event names (`slides.tsx`, `PromptLab.tsx`, `InteractiveLesson.tsx`) are mapped to actions in `lessonEvents.ts:121-415` and sent by `useLessonTracking.ts:83-99`. Each lesson row in the CSV cites both the mapping line and the trigger line.
4. Grepped all writes to `activity_logs` (`activityLog.create/createMany`, `.record(`, `recordBatch`). Python workers do not write to it.
5. Read `rules.ts` (all 36 `RuleDef`s), `prepare.ts`, `learning-events.service.ts:135-300` and `library.v2.json` to see which rules use which actions.
6. Ran read-only frequency queries on the local dev database (see A2).

### Common envelope (applies to every activity_logs row)

`id` (a server-generated UUID), `session_id`, `user_id`, `action`, `occurred_at`, the optional FK columns `course_id`, `module_id`, `module_item_id`, `assessment_id`, `attempt_id`, `question_id`, `dialogue_session_id`, `intervention_id`, and `metadata` JSON (`schema.prisma:1674-1704`).

- `occurred_at` is **client wall-clock time for browser rows** (`ActivityLogContext.tsx:147`) and **server time for server rows** (`activity-log.service.ts:45`; the nudge row uses the database default).
- There is **no** server-received time, client event id, global sequence number, app build version, consent scope or content version.
- Only interactive-lesson events carry a sequence number: `metadata.seq`, which is per page load and restarts on reload (`useLessonTracking.ts:77-93`).
- `kcId` exists on the web event type (`types.ts:118`), but it is neither a column nor in the Zod schema, so it is silently dropped (`log-event.dto.ts:14-28`).

### Notable findings

1. **`INTERVENTION_TRIGGERED` has two meanings.** It is written for learner-launched or pre-generated strategies (`learning-interventions.service.ts:1981,2189,2527,2621,2978,3061,3394,3493`, `triggerReason: student_initiated | pre_generated`) and for system nudges (`nudge.service.ts:293-306`, `triggerReason: rule_triggered`). M34 "intervention uptake" uses both without telling them apart (`rules.ts:914-960`). In the local DB all 308 rows are learner-initiated (296) or pre-generated (12), with 0 rule-triggered, so all 30 local M34 events describe strategy use the learner chose, not uptake of a system intervention.
2. **Stepwise force-pass.**
   - After the maximum number of attempts the server sets `passed = true` and `showAnswer = true` (`learning-interventions.service.ts:3164-3181`).
   - The client counts these steps in `INTERVENTION_COMPLETED.metadata.stepsPassed` (`StepwiseLearningView.tsx:447-460`). So "passed" does not mean "answered correctly".
   - The per-step `QUESTION_ANSWERED` still carries `isCorrect`, `attempts` and `showAnswer` (`StepwiseLearningView.tsx:304-322`), so correctness can be recovered only at the event level.
3. **The same action fires from two places (double emitters).**
   - `SPACED_REP_CARD_RATED` (`ReviewQueuePage.tsx:434` and `learning-interventions.service.ts:3581`): exactly 127 + 127 rows locally.
   - `ASSESSMENT_STARTED` (`StudentAssessmentsPage.tsx:72` and `attempts.service.ts:81,136`) and `ASSESSMENT_SUBMITTED` (`AttemptPage.tsx:293` and `attempts.service.ts:291`).
   - `DIALOGUE_SESSION_STARTED` (`DialogueLearning.tsx:391,454` and `dialogue.service.ts:82`) and `DIALOGUE_MESSAGE_SENT` (`DialogueLearning.tsx:459,482` and `dialogue.service.ts:366`).
   - `WEBGAZER_CALIBRATION_STARTED/COMPLETED` (`BiometricsWrapper.tsx:139,191` and `webgazer.controller.ts:70-75`).
   - Each copy has different metadata and a different clock. `prepareActions` removes only byte-identical copies (`prepare.ts:28`), so none of these pairs is collapsed.
   - In the Prompt Lab, a regeneration writes both `PROMPT_SUBMITTED` and `OUTPUT_REGENERATED` for the same `runId` (`PromptLab.tsx:229,249`).
4. **The last slide of a session loses its `SLIDE_EXITED`.**
   - Locally there are 121 `SLIDE_ENTERED` and 94 `SLIDE_EXITED` rows. In 27 of the 34 lesson sessions, the last lesson event is a `SLIDE_ENTERED` with no exit.
   - `exitReason` counts: navigate 83, pagehide 10, unmount 1.
   - The unmount and logout paths (`useLessonTracking.ts:200-204`) almost never deliver. A likely cause: the unmount `track()` runs after `clearActivitySession`, when `flush()` returns early with no session id (`ActivityLogContext.tsx:134`) and the buffer is then cleared (`:89`).
   - This cannot be proven statically. **Runtime check (Prompt E):** log out while on a slide, and separately navigate from a lesson to the home page; then count SLIDE_EXITED rows with `exitReason=unmount`.
   - Note that part of the local data comes from automated browsers, which may close the context without `pagehide`.
5. **Free text bypasses text-capture consent.**
   - Server-side stripping only touches events that carry `libraryVersion` and a `text`/`parts` key (`apps/api/src/governance/text-consent.service.ts:67-97`).
   - Stored regardless of consent:
     - `CHATBOT_MESSAGE_SENT.metadata.message` (1000 chars, `ChatbotPanel.tsx:419-428`)
     - `CHATBOT_MESSAGE_RECEIVED.metadata.reply`
     - `DIALOGUE_MESSAGE_SENT.metadata.messageText` (full text, `dialogue.service.ts:366-376`)
     - `QUESTION_ANSWERED.metadata.answer` (500 chars, `PracticeTestingView.tsx:319-335`, `StepwiseLearningView.tsx:321`)
     - `click_logs.elementText` (50 chars of `innerText`, `useInteractionLogger.ts:212`)
     - `chatbot_messages.content`
6. **Paste provenance covers only Prompt Lab outputs.** `matchPaste` compares against outputs stored by `rememberOutput`, which only the Prompt Lab calls (`prompt-lab/aiOutputs.ts:26,39`; `PromptLab.tsx:144,228,589`). A paste of a Learning Assistant reply into a lesson field is logged with `matchesAiOutput: false` (`InteractiveLesson.tsx:265-282`), so M31 and M32 cannot see reliance on the chatbot.
7. **The chatbot turn record is thin.**
   - `CHATBOT_MESSAGE_SENT` has no message id. M08 matches classifier labels to it by ±10 s (`rules.ts:309-318,328`).
   - The action row has no latency, model, context source or selection source; `chatbot_messages` holds `contextSource` and `model` but is not linked by id (`learning-interventions.service.ts:4511-4545`).
   - "Ask about this slide" fills `selectedText` (`ChatbotPanel.tsx:1166-1179`), so it is logged as `hasSelection: true`, the same as a manual highlight.
   - Failed replies log nothing.
   - In Mode B both dialogue rows are written after the reply, so `SENT` and `RECEIVED` share a timestamp (`dialogue.service.ts:366-388`).
8. **Overloaded names.**
   - `MODULE_ITEM_VIEWED` is both an item selection (`StudentCourseViewPage.tsx:557`) and a page view on every route change (`usePageViewTracker.ts:26`, mounted at `Layout.tsx:18`). It is the third most frequent action locally (3929).
   - `MODULE_OPENED` is really a course open (`StudentCourseViewPage.tsx:540`).
   - `QUESTION_ANSWERED` covers four different behaviours: practice answer, stepwise check, flashcard transition and elaboration question.
   - `SPACED_REP_CARD_VIEWED` means "front shown" in `DistributedPracticeView.tsx:136` and "back shown" in `ReviewQueuePage.tsx:404`.
9. **Content version is missing from events.** Every slide has a `contentHash` (`apps/api/src/interactive-lesson/course-html-parser.ts:144,153`), but no event carries it. Lesson events carry only `libraryVersion: 'v2'` (`lessonEvents.ts:16,129`). `slideKey` is positional, `s<session>-<index>` (`course-html-parser.ts:152`), so inserting a slide renames every later one.
10. **System feedback is not logged.** Checkpoint AI feedback (verdict and text) is stored only by overwriting `lesson_slide_states.state.fields.aiFeedback` (`interactive-lesson.service.ts:229-240`). No event records that feedback was requested, shown or failed. `FEEDBACK_RECEIVED` has no emitter.
11. **Newly added emitters, verified.**
    - Study notes: `NOTE_CREATED/EDITED/DELETED`, `HIGHLIGHT_CREATED/DELETED` and `NOTES_VIEWED` (`apps/web/src/lib/notes/NotesContext.tsx:115-221`). They carry ids, lengths and the anchor only, never text. M04 uses NOTE_CREATED/NOTE_EDITED when `chars > 0` (`rules.ts:247-262`).
    - Camera guard: `CAMERA_BLOCKED/RESTORED` (`CameraGuard.tsx:34-40`).
    - EF puzzles: 6 server-only EF\_\* actions (`efa/occasion.service.ts:240,389,474,481`; `efa/task-run.service.ts:77,165`). Rules drop them (`prepare.ts:24`).
    - Knowledge tests: 4 browser actions and 2 server-written ones (`KnowledgeTestPage.tsx:95-203`; `knowledge-test.service.ts:197,360`).
    - Checkpoint AI feedback: no action at all (finding 10).

Scope: branch `course-prompting-kt`, HEAD `acee9b6`. Read-only static audit plus read-only SELECTs against the **local dev database** (`localhost:5432/ats_db`, from `apps/api/.env`). ## A4. Transport reliability (R11)

### A4.1 Click-to-row path (one MCQ answer on an interactive-lesson slide)

1. **Emit.** The slide component calls `emit` → `useLessonTracking.send` (`apps/web/src/components/interactive-lesson/useLessonTracking.ts:83-97`), which adds `courseId`, `moduleId`, `moduleItemId` and `metadata.seq = ++seq.current` (`:92`). `seq` is per hook instance (per lesson mount) and resets on every mount (`:77-79`).
2. **Buffer.** `ActivityLogContext.track` pushes `{action, occurredAt: new Date().toISOString(), ...extras}` into an in-memory `useRef` array (`apps/web/src/lib/activity-log/ActivityLogContext.tsx:142-152`, buffer at `:75`). No event id, no page-load id, no persistence.
3. **Flush triggers.** 30 s interval (`:33`, `:155-160`); `visibilitychange→hidden` and `pagehide` with `keepalive` (`:165-195`); explicit `flush()` from the chatbot/lesson/survey/knowledge-test pages (`apps/web/src/components/interactive-lesson/InteractiveLesson.tsx:99`, `apps/web/src/components/Layout.tsx:36`, `apps/web/src/pages/student/knowledge/KnowledgeTestPage.tsx:213`); the logout flush event (`ActivityLogContext.tsx:181-185`, dispatched by `apps/web/src/contexts/AuthContext.tsx:265-266`).
4. **Send.** `send()` splits into ≤500-event chunks (and ≤60 KB per chunk when keepalive) (`ActivityLogContext.tsx:37-58`, `:104`) and POSTs `/api/activity-log/batch` with `Authorization: Bearer <localStorage token>` and `X-Session-Id` (`:106-115`).
5. **nginx public door.** Exact-match allow `location = /api/activity-log/batch` (POST only) (`deploy/nginx/snippets/public-api-allowlist.conf:96`), body cap 16 MB (`deploy/nginx/snippets/proxy-api.conf:20`).
6. **Nest guards.** Global `ThrottlerGuard` (30 req / 60 s per route per client IP) and `DoorGuard` (`apps/api/src/app.module.ts:62-72`, `:136-141`); `JwtAuthGuard` + `RolesGuard` (`apps/api/src/activity-log/activity-log.controller.ts:38`, `:72`). DoorGuard treats it as public because `@Roles` includes `student` (`apps/api/src/common/door/door.guard.ts:67-78`).
7. **Validation.** `ZodValidationPipe(BatchLogEventsSchema)` on the whole body (`activity-log.controller.ts:74`; schema `apps/api/src/activity-log/dto/log-event.dto.ts:52-73`).
8. **Ownership.** `assertOwnsSession` (exists + same user; does **not** check `endedAt`) (`apps/api/src/activity-log/session.service.ts:75-84`).
9. **Consent scrub.** `stripUnconsentedText` deletes text keys, never drops events (`apps/api/src/governance/text-consent.service.ts:73-99`).
10. **Insert.** `recordBatch` → `prisma.activityLog.createMany({skipDuplicates:true})`; errors are caught and logged, and the controller still returns `{ok:true}` (`apps/api/src/activity-log/activity-log.service.ts:67-92`, `activity-log.controller.ts:83-100`).
11. **Row.** `activity_logs` (`apps/api/prisma/schema.prisma:1674-1704`): DB-generated `id`, `occurred_at` = the browser's clock, no received-at column, no client event id, no sequence column.
12. **Parse later.** Only on `session.closed` (`session.service.ts:174` → `apps/api/src/learning-events/learning-events.service.ts:115-125`).

The parallel click-stream path: `click` listener → `clickBuffer` (`apps/web/src/lib/interaction-log/useInteractionLogger.ts:205-216`) → 30 s `api.post('/logs/clicks')` (`:101-118`, `:480-482`) → nginx `^~ /api/logs/` (`public-api-allowlist.conf:99-101`) → `LogsController.batchClicks` with **no runtime validation and no ownership check** (`apps/api/src/logs/logs.controller.ts:18-34`) → `click_logs` (`schema.prisma:1980-1992`, client epoch-ms `timestamp`, no FK to `student_sessions`).

## A5. Session lifecycle (R5)

**Creation.** A `StudentSession` is created at login (`apps/api/src/auth/auth.service.ts:499-511` → `session.service.ts:87-119`, which also writes a server-time `SESSION_START`), or, when a student tab already holds a token but `sessionStorage` has no `ats_session_id` (a new tab, or a tab whose storage was cleared), by `POST /activity-log/session/open` (`AuthContext.tsx:116-128`, `activity-log.controller.ts:58-65`). **Resume.** A reload in the same tab keeps `sessionStorage`, so it keeps the same session (`ActivityLogContext.tsx:71-73`). There is no token refresh: the JWT lasts 24 h (`apps/api/src/auth/auth.module.ts:30`). **Close.** All paths end in `SessionService.closeSession` (`session.service.ts:134-178`). It sets `endedAt`/`durationSecs`, writes `SESSION_END` with `metadata.reason` (`logout` or `timeout`), builds the summary, and emits `session.closed`. A timeout never re-closes a closed session, but a logout or close call does (`session.service.ts:143-145`).

### A6.1 How the parser runs

1. Trigger: `@OnEvent('session.closed', { async: true })` → `computeSession` (`apps/api/src/learning-events/learning-events.service.ts:115-125`). `session.closed` is emitted by `SessionService.closeSession` (`apps/api/src/activity-log/session.service.ts:174`), which now also runs from the 2 h `SessionTimeoutSweeper` (`apps/api/src/activity-log/session-timeout.sweeper.ts:6-15`). Manual: `POST sessions/:id/recompute`, `POST courses/:id/recompute` (`learning-events.controller.ts:136-155`) and the CLI `learning-events:backfill` (`apps/api/package.json:23`, `apps/api/prisma/scripts/backfill-learning-events.ts:21-41`). A parse failure is only logged as a warning (`learning-events.service.ts:119-124`).
2. Parameter set: the given version, otherwise the **latest** version (`learning-events.service.ts:63-66,134-140`); resolved by overlaying the stored overrides on the defaults read at runtime from `library.v2.json` (`engine/params.ts:28-62`). Version 1 is created with `values: {}` (`learning-events.service.ts:68-76`).
3. Inputs: all `activity_logs` rows of the session, **no `orderBy`** (`learning-events.service.ts:142-153`); `prepareActions` drops server-only actions and double-posted copies keyed on `action|at|stableStringify(meta)`, first row seen wins, then sorts by client time, `seq`, row id (`engine/prepare.ts:17-35`). Plus `visibility_logs` (`learning-events.service.ts:156-164`), prior visits/commits from earlier sessions (`:236-271`), current rule statuses (`:226-234`) and **all** `ai_prompt_classifications` of the student within the session span ±60 s, any classifier version (`:168-186`).
4. Rules: `runRules` = every `RULES[i].run(input)`, flattened and sorted by start then ruleId (`engine/rules.ts:1027-1031`). Rules are independent functions; there is no parser state machine, no lookahead window shared across rules, and no global precedence step.
5. Persistence: one transaction `deleteMany({ sessionId })` then `createMany(data)` (`learning-events.service.ts:208-211`). Each row gets a fresh `@default(uuid())` id (`apps/api/prisma/schema.prisma:2724`). The run summary (`rawActions`, `duplicatesRemoved`, `byRule`) is returned to the caller but not stored (`learning-events.service.ts:212-222`).

### A6.4 Recompute: determinism, idempotency, id stability

- **Idempotent in content, not in identity.** A recompute replaces the session's rows in one transaction (`learning-events.service.ts:208-211`). Given unchanged inputs, the same set of `(ruleId, outcome, startAt, endAt, sourceActionIds, detail)` rows is produced, but every row gets a **new UUID** (`schema.prisma:2724`) and a new `computedAt`. There is no natural key or unique constraint on `learning_events` (`schema.prisma:2747-2750`; `apps/api/prisma/migrations/20261007150000_add_learning_events/migration.sql:3-43`), so upsert is impossible today. **Ids are not stable across recomputes.** Any verdict keyed on `learning_events.id` would be orphaned by the next recompute, session close or backfill.
- **Old versions are destroyed.** `deleteMany({ where: { sessionId } })` ignores `parameterSetVersion` and `libraryVersion`, so recomputing under parameter set 2 deletes the set-1 rows; the Phase 7 test does exactly this and then recomputes back (`apps/api/src/learning-events/phase7.integration.spec.ts:367-377`). There is no per-version history (V7).
- **Deterministic only relative to mutable state.** The rule functions are pure and ordering is total (`engine/prepare.ts:33`; `engine/rules.ts:1028-1030`). But the output also depends on: which copy of a double-posted row comes first from an unordered query (affects `sourceActionIds`; `learning-events.service.ts:142-153`, `engine/prepare.ts:28-31`); whether the classifier has run since, and under which version (`learning-events.service.ts:174-186`); current rule statuses (`:167,202`); the latest parameter set at the time (`:134-138`); runtime defaults in `library.v2.json` for any set (`engine/params.ts:49-62`); and late-arriving raw rows. None of these inputs is recorded on the row.
- **Concurrency.** `session.closed` handling is async (`learning-events.service.ts:115`) and a manual or course recompute can run at the same time; with delete-then-insert and no unique key, two overlapping transactions can both insert, duplicating a session's events (`:208-211`). Not observed; to check at runtime in Prompt E.
- **Version mixing.** Auto-parse always uses the latest set (`:63-66`), so once a researcher adds a set, every newly closed session uses it while older sessions keep the set they were computed with. Coverage, validation and exports read rows without filtering or grouping by `parameterSetVersion` (`learning-events.service.ts:319-322`; `validation/validation.service.ts:99-102`; `exports/exports.service.ts:196-199`).
- **A second, live copy of the engine.** Nudge evaluation re-runs `runRules` on the last window of actions with empty visibility and empty prior history (`apps/api/src/learning-events/nudges/nudge.service.ts:190-226`), keyed by sorted source action ids (`:248-252,286-288`), without recording parameter set or library version. Its outputs can differ from the stored learning events for the same actions (e.g. M03 vs M03b without prior visits). The nudge `sourceKey` is, however, a precedent for a content-derived key.

### A6.5 Coverage and NO_PATTERN / UNRESOLVED (R7, A5)

- **No `NO_PATTERN` or `UNRESOLVED` exists.** No such label, status or table anywhere in `apps/api/src`, `tools/gals-export/src` or `gals-studio` (repo-wide search; the only "unresolved" hits are unrelated, in `code-decomposition` and Studio affect analysis). `Draft` has no status or alternatives field (`engine/types.ts:47-56`).
- **Missing fields are forced into a label or silently dropped, never surfaced.** Forced: M07 `incorrect` when `correct` is absent (`rules.ts:298`); M05 when `chars` or `msOnSlide` is absent, because `isLowEffort` returns false on non-finite values (`rules.ts:110-117,270`); M16 reads a missing `choice` as a correct commit (`rules.ts:459`); M08 `untyped` (`rules.ts:322`). Dropped: a reveal with no matching commit (M15, `rules.ts:409`); a prompt with no matching view (M28, `rules.ts:756`); a pasted-and-verified output with no qualifying edit (neither M31 nor M32, `rules.ts:864-877`); a low-effort `think` commit (neither M05 nor M24, see inconsistencies).
- **Competing matches are emitted side by side, not resolved.** One action yields several labels with no precedence: `PROMPT_GOAL_DECLARED` → M02 and M26 (`rules.ts:182-185,693-699`); `MCQ_ANSWERED` → M06 and M07 (`:283-299`); `SELF_CHECK_SUBMITTED` → M14 and M15 (`:375-376,403-421`); a chatbot message → M08 and M33 (`:310-343`); every closed off-task interval → M25 and M20 `interruption_resumed` (`:522-533,558-566`); idle and hidden intervals overlap and each produces M25 (`:487-516`). Explicit exclusivity exists only for M03/M03b/M21 (`:204-220`), M05/M24 (`:270`), M31/M32 (`:855-863`) and M01 vs M14 (`:166`).
- **No unclassified-time measure.** Nothing computes active time, the union of event intervals, or the share of active time covered (A5, V2 trace coverage). M25 marks `excludedFromTimeOnTask: true` (`rules.ts:531`) but nothing consumes it.
- **Coverage report.** `GET /learning-events/courses/:courseId/coverage` (`learning-events.controller.ts:157-164`) → `LearningEventsService.coverage` (`learning-events.service.ts:307-348`). Per rule it returns sessions where any of `RuleDef.inputs` occurred (`couldFire`), sessions with ≥ 1 row (`fired`), their shares, and `status ∈ {no_input, zero_coverage, ok}` with the `notApplicable` reason. It is a session-presence count, not a time share. `couldFire` is coarse: M03b, M21, M20, M25 list `SLIDE_ENTERED`/`IDLE_STARTED` as inputs (`rules.ts:233,237,521,537`), so nearly every session "could fire" them; M33 lists `PROMPT_SUBMITTED`/`CHATBOT_MESSAGE_SENT` though it fires from classifications (`:332`); visibility logs are ignored; the `groupBy` over raw rows includes server-only actions and duplicates (`learning-events.service.ts:309-312`). It cannot distinguish "session never parsed / parse failed" from "parsed, no events", because no parse run is recorded. The `libraryVersion` it returns is the code constant, not the rows' versions (`:347`).

### A7.1 Format

**Layout.** One folder `session_<sessionId>/`, optionally zipped to `session_<sessionId>.zip` (`tools/gals-export/src/export.ts:57`, `:228-233`; zip via archiver level 9, `tools/gals-export/src/writer.ts:63-73`):

```
messages/  chatbot dialogue interventions ef_detections (.jsonl)
kc/        cards attempts (.jsonl)

probes/ questionnaires/ annotations/        (optional, omitted when empty; never populated today)
snapshots/ index.json + <id>.html + <id>.jpg

```

Stream map: `tools/gals-export/src/types.ts:95-120`; optional streams `:131-137`; spec `tools/gals-export/BUNDLE_SPEC.md:14-40`, `:151-160`.

**Schema version.** `bundleVersion: 1`, `exporterVersion: '1.0.0'` (`tools/gals-export/src/types.ts:9-10`). The `derived/learning_events.jsonl` stream was added without a version bump. Studio accepts only the literal `1` (`gals-studio/packages/shared/src/bundle/schemas.ts:13`), and the exporter's own validator rejects anything else (`tools/gals-export/src/validate.ts:41`). There is no platform schema version, git commit, app build or migration id in the manifest.

**Manifest** (`tools/gals-export/src/types.ts:18-32`, written `tools/gals-export/src/export.ts:208-226`): `bundleVersion`, `exporterVersion`, `exportedAt`, `sessionId`, `userId` (raw platform UUID, not a pseudonym), `courseId`, `moduleId?` (module of the last activity row with one, `tools/gals-export/src/datasource.ts:86-95`), `timezone` (from the sync anchor, else `UTC`), `baseWallClockMs`, `durationMs`, `counts` (rows per stream), `files` (path to `{sha256, byteSize}`), `notes[]` (per-stream fetch failures, missing webcam, snapshot decode failures).

**Checksum scheme.** SHA-256 over the exact bytes of every written file, computed while writing (`tools/gals-export/src/writer.ts:24-33`; streamed for JSONL `:39-60`). `manifest.json` is written last and is not itself checksummed (`tools/gals-export/src/export.ts:224-226`). Verification: `verifyChecksums` (`tools/gals-export/src/writer.ts:77-93`), used by the exporter's validator (`tools/gals-export/src/validate.ts:43-44`); Studio re-hashes on import but treats mismatches as warnings (`gals-studio/packages/shared/src/bundle/validate.ts:82-93`). There is no signature, no bundle id, and no hash of the manifest.

**Time anchor.** `baseWallClockMs = min(session_sync_anchors.wallClockMs, first snapshot capturedAt, student_sessions.startedAt)` (`tools/gals-export/src/export.ts:117-123`). `durationMs = max(wallMs over session-scoped streams, snapshots and webcam ends) - base`, falling back to `durationSecs` then `endedAt` (`:202-206`). Since `69893a8`, `cards` and `attempts` (`USER_SCOPED_STREAMS`, `tools/gals-export/src/types.ts:128`) are excluded from the max (`tools/gals-export/src/export.ts:129-134`). All records carry absolute `wallMs`; the anchor's `monotonicMs` and `serverReceiveMs` are written to `session.json` (`tools/gals-export/src/datasource.ts:126-134`) but not used to correct anything.

**Robustness and determinism.** A failing stream is logged in `notes`, its count set to 0 and, if not optional, an empty file is written (`tools/gals-export/src/export.ts:143-148`); the export never fails for a stream. An existing bundle is not overwritten without `--force` (`:59-66`). The "byte-identical rerun" promise (`tools/gals-export/BUNDLE_SPEC.md:243-244`) does not hold for `kc/cards.jsonl`, which is queried without `orderBy` (`tools/gals-export/src/datasource.ts:467-469`).

**Which Prisma client.** The exporter loads `@prisma/client` dynamically (`tools/gals-export/src/cli.ts:66-73`), which resolves to the exporter's own generated client in `tools/gals-export/node_modules/.prisma/client` (generated 7 Oct, Prisma 6.19.2). It is built from `tools/gals-export/prisma/schema.prisma`, a hand-maintained subset of `apps/api/prisma/schema.prisma` (26 vs 37 enums; no Prompt Lab, slide-state, consent, knowledge-test, EF-battery, nudge, parameter-set or study-note models). The README says it reuses "the live `@prisma/client`" (`tools/gals-export/README.md:8`, `:16`), which is not what happens.

### A7.3 Consent-gated text

- **Capture time (platform).** The activity-log batch strips `text` and `parts` from lesson / Prompt Lab events unless consent (a) `answerText` is given for that course (`apps/api/src/governance/text-consent.service.ts:67-99`, called from `apps/api/src/activity-log/activity-log.controller.ts:80-81`). Prompt Lab prompt/output text without consent (b) is blanked at `session.closed` (`apps/api/src/governance/text-consent.service.ts:101-156`), i.e. not for sessions that end by tab close.
- **Export time.** Consent (c) `researchUse` is applied **only to `derived/learning_events.jsonl`**: rows are dropped unless the learner's latest `text_capture_consents` row for the course has `research_use = true` (`tools/gals-export/src/datasource.ts:497-514`). When every row is dropped the optional file disappears (`tools/gals-export/src/export.ts:137-141`) and nothing in the manifest says why.
- **Not gated at export:** activity metadata (incl. consented answer text), chatbot `content` and `selectedText`, dialogue `content`, intervention `selectedText` and `sessionData` (typed answers), card `front`/`back`, click `elementText`, raw DOM snapshot HTML and screenshots, webcam video (`tools/gals-export/src/datasource.ts:296`, `:351-488`; `tools/gals-export/src/export.ts:74-196`). So a learner who refused (c) still has every raw stream exported; only the derived events are withheld. `session.json` also carries the learner's display name (`tools/gals-export/src/datasource.ts:135-139`) and the manifest the raw `userId`.
- The platform's own CSV exports apply (c) to the whole learner and pseudonymise (`apps/api/src/learning-events/exports/exports.service.ts:21`, `:54`, `:62`); the bundle does neither.
