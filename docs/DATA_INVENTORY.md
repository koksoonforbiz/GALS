# Personal & Sensitive Data Inventory

Satisfies SMU Cybersecurity Checklist item 37 ("maintained inventory of personal/
sensitive data with classification, location, retention"). Also informs items 32-35
(encryption, consent) and the `/terms` notice shown to students at registration.

Generated by reading `apps/api/prisma/schema.prisma` directly — this is a snapshot
of what the schema _currently_ collects, not a policy document. **PDPA
classification and the retention periods below are drafted for review, not yet
signed off by SMU's legal/PDPA office** — treat every "recommend" line as a
proposal, not a committed policy.

## How to keep this current

Every table below maps to a Prisma model. When a migration adds a new model that
stores anything about a real person, add a row here in the same pass — this
document decays the moment schema and inventory diverge.

## 1. Identity & account data

| Data                     | Table(s)                                                                                | Classification               | Notes                                                                                            |
| ------------------------ | --------------------------------------------------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------ |
| Name, email, role        | `User`                                                                                  | Personal                     | Also `loginId` for bulk-provisioned students.                                                    |
| Password hash            | `User.passwordHash`                                                                     | Sensitive (credential)       | bcrypt, cost 10 — never stored/logged in plaintext.                                              |
| Password history         | `PasswordHistory`                                                                       | Sensitive (credential)       | Last 3 hashes per user, reuse-prevention only.                                                   |
| Per-teacher LLM API keys | `User.encryptedApiKey`, `cohereApiKey`                                                  | Sensitive (secret)           | AES-256-GCM at rest; not personal data about the _teacher_, but a credential that must not leak. |
| TOTP secret              | (2FA table, AES-256-GCM encrypted)                                                      | Sensitive (credential)       | Opt-in 2FA enrollment.                                                                           |
| Account status / lockout | `User.isActive`, `deactivatedAt`, `deactivatedBy`, `failedLoginAttempts`, `lockedUntil` | Personal (security metadata) | Added this pass — see checklist items 5, 11.                                                     |
| Terms-of-use acceptance  | `User.termsAcceptedAt`                                                                  | Personal (consent record)    | Added this pass — see checklist item 35.                                                         |

**Recommend retention**: for the life of the account + a fixed post-departure
window (e.g. matching SMU's academic record retention policy) before anonymizing
`name`/`email` on `User` rows tied to closed accounts — needs a decision from
SMU's PDPA office on the exact window, not something to invent in code.

## 2. Learning activity & assessment data

| Data                                | Table(s)                                                       | Classification              | Notes                                    |
| ----------------------------------- | -------------------------------------------------------------- | --------------------------- | ---------------------------------------- |
| Enrollment, course/module structure | `Enrollment`, `Course`, `CourseModule`, `ModuleItem`           | Personal (education record) | Standard LMS-shape data.                 |
| Quiz/assessment attempts and grades | `Attempt`, `GradingResult`, `Assessment`, `AssessmentQuestion` | Personal (education record) | Core to the platform's research purpose. |
| Spaced-repetition / review state    | `SpacedRepetitionCard`                                         | Personal (education record) | Per-student scheduling state.            |

**Recommend retention**: education records typically follow the course/semester
retention schedule SMU already has for LMS data — apply the same schedule here
rather than defining a separate one.

## 3. AI tutoring interactions

| Data                                  | Table(s)                                             | Classification                  | Notes                                                                                                                                                                        |
| ------------------------------------- | ---------------------------------------------------- | ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Full chat prompt + response text      | `ChatbotMessage`                                     | Personal, potentially sensitive | Stores the complete conversation, including any highlighted source text the student selected (`selectedText`). This is the fullest record of what a student typed to the AI. |
| Dialogue-mode sessions                | `DialogueSession`, `DialogueMessage`, `DialogueNote` | Personal, potentially sensitive | Same shape as above for the Socratic-dialogue surface.                                                                                                                       |
| LLM call audit trail                  | `LlmAuditLog`                                        | Personal (metadata-level)       | Full _query_ text, but only output _metadata_ (not full output text) — a deliberately smaller footprint than `ChatbotMessage`.                                               |
| LLM cost/usage                        | `LlmUsageLog`                                        | Non-personal                    | Token counts and cost only, no content.                                                                                                                                      |
| Teacher-authored intervention prompts | `InterventionPromptConfig`, `FeedbackPromptConfig`   | Not personal                    | Configuration, not student data.                                                                                                                                             |

**Why this matters for item 63 (PII filtering)**: `ChatbotMessage.content` and
`selectedText` can contain anything a student pastes in, including PII about
themselves or others. There's still no filtering/redaction — that remains an open
product decision (see the checklist audit) since it's in tension with the
grounding contract's "faithfully reproduce the source" instruction. What now
exists: a best-effort, non-blocking PII detector
(`apps/api/src/rag/shared/pii-detection.ts`) runs on every chatbot/dialogue reply
and logs a warning (email/phone/SG NRIC-FIN/credit-card/SSN-shaped matches) —
visibility for a future decision, not a fix. Content is never altered.

**Recommend retention**: shortest of (a) the research study's IRB-approved
retention period, or (b) course completion + N months — again, needs the study's
actual IRB protocol, not a value invented here.

## 4. Behavioral & interaction telemetry

This is the platform's largest category by table count and the one most likely to
surprise a student if they only read a generic privacy notice — worth the most
explicit treatment in the `/terms` page.

| Data                        | Table(s)                                                                                                                         | Classification                | What's actually stored                                                                                                                                                                                                                           |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Mouse/scroll/click          | `cursor_logs`, `click_logs`, `scroll_logs`, `viewport_logs`, `visibility_logs`                                                   | Personal (behavioral)         | Coordinates, page URL, timing. No content.                                                                                                                                                                                                       |
| Keystroke _timing_          | `keystroke_logs`                                                                                                                 | Personal (behavioral)         | **Not raw keystrokes** — only `keystrokeCount`, `pauseDurationMs`, `typingSpeedWPM` per field. Privacy-conscious design already in place; worth stating explicitly in the `/terms` copy so "keystroke logging" doesn't sound scarier than it is. |
| Clipboard _activity_        | `clipboard_logs`                                                                                                                 | Personal (behavioral)         | **Not clipboard content** — only `action` (copy/paste/cut), `textLength`, source element. Same design pattern as keystrokes: metadata, not content.                                                                                              |
| Performance/error telemetry | `performance_logs`, `error_logs`                                                                                                 | Non-personal (mostly)         | Client performance metrics; may incidentally include a user id for correlation.                                                                                                                                                                  |
| Session bookkeeping         | `StudentSession`, `session_sync_anchors`, `modality_offsets`                                                                     | Personal                      | Ties the above streams to a wall-clock timeline per session.                                                                                                                                                                                     |
| Derived analytics           | `derived_engagement`, `derived_cognitive_load`, `derived_emotion_timeline`, `derived_learning_velocity`, `derived_at_risk_flags` | Personal (inferred/sensitive) | Model _outputs_ about a student's engagement/emotional state — arguably more sensitive than the raw signals they're derived from, since they're evaluative judgments about the student.                                                          |

**Recommend retention**: raw event-level tables (`cursor_logs` etc.) are the best
candidate in the whole schema for an aggressive retention window (e.g. 90 days)
since their research value is in aggregate derived metrics, not the raw stream —
but this is a research-design call, not one to make unilaterally in code.

## 5. Biometric data (highest sensitivity category)

| Data                     | Table(s)                                                                    | Classification                    | What's actually stored                                                                                                                                                                                                                                |
| ------------------------ | --------------------------------------------------------------------------- | --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Webcam/screen recordings | `RecordingSegment` (+ `RecordingConfig`)                                    | **Sensitive — biometric**         | Actual video files in MinIO object storage (`minioKey`); Postgres holds only metadata (duration, size, mime type). Opt-in per course via `RecordingConfig.isEnabled`; per-student consent captured in `RecordingConsent`.                             |
| Facial emotion inference | `EmotionFrame`, `Openface3Job`, `EfDetection`                               | **Sensitive — biometric-derived** | Per-frame emotion probabilities (happiness/sadness/anger/etc.), dominant emotion, head pose. Derived from the recordings above via the OpenFace3 worker — never raw facial imagery once processed, but still a biometric inference about the student. |
| Pupil size               | `PupilSizeConfig`, `PupilSizeLog`                                           | **Sensitive — biometric**         | Pupil diameter over time, optionally `rawData` JSON blob.                                                                                                                                                                                             |
| Gaze tracking            | `WebgazerConfig`, `WebgazerLog`, `WebgazerCalibrationEvent`                 | **Sensitive — biometric**         | Gaze x/y coordinates, confidence, calibration accuracy.                                                                                                                                                                                               |
| Facial action units      | `PyfeatConfig`, `PyfeatJob`, `PyfeatAuResult`                               | **Sensitive — biometric-derived** | py-feat action-unit intensities, a research-grade facial-expression signal.                                                                                                                                                                           |
| Replay reconstruction    | `SessionReplaySnapshot`, `ReplayCode`, `ReplayAnnotation`, `aligned_frames` | Personal (composite)              | Reassembles the above streams into a synchronized timeline for teacher/researcher review — a single replay can combine gaze + emotion + code + video references for one session.                                                                      |

**This is the category PDPA scrutiny will focus on first.** All of it is already
gated behind a per-course `isEnabled` config flag and (for recordings specifically)
an explicit `RecordingConsent` record — but consent is currently scoped to
recording only, not to the derived-biometric pipelines individually. Worth a
PDPA-office read on whether one recording consent checkbox is sufficient cover for
gaze/pupil/emotion inference too, or whether each needs its own opt-in.

**Recommend retention**: shortest defensible window given this is the highest-risk
category — but the _right_ number depends entirely on the study's IRB protocol,
not something to set here.

## 6. What is NOT collected

Worth stating explicitly, since the absence is as relevant to a PDPA review as the
presence:

- No raw keystroke content (see §4).
- No raw clipboard content (see §4).
- No government ID numbers, financial data, or health records anywhere in the schema.
- No third-party tracking/advertising pixels — all telemetry above is first-party,
  captured by GALS's own frontend and sent directly to the GALS API.
- No LLM fine-tuning or training pipeline (checklist item 54) — chat content is
  stored for the platform's own research/product purposes, never sent onward to
  train a model.
